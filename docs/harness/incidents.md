# 事故台帳 — 各ゲートが「どの事故から生まれたか」

このハーネスの各ゲートには、それを作らせた具体的な事故があります。
**閾値も検査軸も、机上で設計したものではありません。**

以下は 2026-03 から 2026-08 までの実運用（1 人 + AI エージェント体制・
コミット約 3,900 件）で起きた事故のうち、ゲート化に至ったものです。
固有名詞・内部パス・顧客名は除去し、**構造だけを残して**います。

各項目の読み方:

- **症状** — 表面上どう見えたか
- **構造** — なぜ気づけなかったか（ここが本体）
- **ゲート** — 何を機械化したか。`✅ 同梱` = このハーネスに入っている

---

## A. 「緑」が信用できなくなる系

### A-1. 依存ツールが消え、lint ゲートが 1 ヶ月間「偽の緑」を返し続けた

- **症状**: 全テスト緑（PASS=316）。しかし特定の lint ゲートは**導入以来一度も
  実行されていなかった**。`command -v <tool>` が失敗 → 「未インストールのため skip」
  と表示して **exit 0**。
- **構造**: fail-closed なゲートは「止まる」ので気づけます。**skip 実装は黙って
  緑を返す**ので誰も異常と認識しません。さらに悪いことに、テストスイート側は
  ツール不在を「正常なテスト条件」として隔離モードに埋め込んでいたため、
  本番の欠落と見分けがつきませんでした。原因は環境変数 1 行の欠落で、
  ゲートのコードは 1 文字も壊れていません。
- **教訓**: 「テストが緑」は「検査が走った」を意味しない。
  **skip 理由を「本当に未導入」と「導入済だが解決できない」に分け、後者は異常として鳴らす。**
- **ゲート**: ✅ 同梱 — 各エンジンの `--self-test` は skip を成功として数えません。
  `verify.sh` は「走った本数」を必ず分母つきで出します。

### A-2. フィルタの単数複数取り違えで 98 件を「0 件」と報告し続けた

- **症状**: 定期チェックが `deletable count: 0` を数週間出力。実際の該当は **98 件**。
- **構造**: 走査ループのフィルタが実態と 1 文字違い（`routines/` と `routine/`）で、
  **98 件中 1 件もマッチせずループが 0 回**回っていました。カウンタは初期値 0 のまま。
  出力が `0` だけだったため「98 件走査して 0 件該当」と「そもそも 0 件しか走査していない」を
  **区別できませんでした**。「0 件」は正常系として最も自然な見た目で、
  **成功と沈黙が同じ絵**になります。
- **教訓**: **カウントを出力する処理は、必ず分母も出力する。**「0」は結論ではなく、
  分母とセットで初めて意味を持つ。ハードコードした列挙（prefix・ラベル・ID）は
  実態からドリフトしても誰も気づけないので、フィルタで絞る設計自体を避け、
  全件走査 + 分類にする。
- **ゲート**: ✅ 同梱 — 全エンジンが「対象無」を明示的な状態として持ち、
  走査 0 件を正常系にしません。`verify.sh` は走査 0 件を `❗` で異常扱いします。

### A-3. 実測 CLI の断続エラーを握りつぶし「0 件」に見えた

- **症状**: 状態チェックが「open な項目 0 件」と表示。実際は 25 件。
- **構造**: スクリプトが CLI の終了コードを検査せず `2>/dev/null` で stderr を捨てていた。
  認証は有効で、3 回に 1 回失敗する一時障害でした。「実測した」つもりで、
  **実測の失敗を検知できない**構造。
- **教訓**: **空出力 ≠ ゼロ件。** 実測スクリプトは「成功した実測」と「失敗した実測」を
  出力で区別できなければならない。取得失敗は 0 ではなく `❓ 不明` として扱う。
- **ゲート**: 原則 P2 の終了コード規約（`2` = I/O エラーを `0` と別扱い）として全エンジンに実装。

### A-4. 安全フック 2 本が約 1 ヶ月フリーパスだった

- **症状**: 破壊コマンド・秘密ファイル編集・強制 push が**すべて素通り**していた。
  月次レビューで初めて発覚。
- **構造**: 3 つの独立したバグの重なり。(1) GNU 前提の正規表現オプションを使い、
  BSD 系の標準コマンドでエラー終了 (2) ツール引数を環境変数から読もうとしたが、
  実際の仕様は stdin 経由の JSON で常に空 (3) **パース失敗時に fail-open**。
  (1)(2) でパースが常に失敗し、(3) で常に許可されていました。
- **教訓**: **セキュリティ系フックは fail-closed。** そして
  **フック導入はセルフテスト（block ケースと pass ケースの両方）なしに行わない。**
- **ゲート**: ✅ 同梱 — `destructive-env-guard` が破壊/環境変更コマンド群を
  読み取り専用で監査し、塞がれていない集合を列挙します。
  `gate-forge` は block/pass 両ケースのテスト雛形を含むフック scaffold を生成します。

### A-5. 正規表現の部分一致が正常なパスを誤検知した

- **症状**: 通常の運用ファイルの編集が「秘密ファイルの編集」として拒否された。
- **構造**: パス全体に対する部分一致で、ディレクトリ名に含まれる 6 文字が
  秘密ファイル判定にヒット。約 1 時間の手戻り。
- **教訓**: **正規表現の部分一致は誤検知の温床。** ファイル名分類は basename + glob で行う。
  そして**セルフテストには false-positive 防止ケースを必ず含める**（block ケースだけ
  書くと、全部 block する実装がテストに通ります）。
- **ゲート**: ✅ 同梱 — `gate-forge` の scaffold は block ケースと pass ケースを
  対で生成します。

## B. 「文書」を「状態」と取り違える系

> このカテゴリは**同じ月に 8 例**発生しました。単発のうっかりではなく構造的な失敗です。

### B-1. 3 時間前に実測した状態を、再実測せずに転載した

- **症状**: 朝に実測した「対応待ち」リストを、3 時間後にそのまま別の場所へ再掲。
  その間に対象は完了・却下済みになっていました。
- **構造**: 実測ルールは「起票時」には効いていましたが、**転載・再パッケージ・要約する
  瞬間の再実測ルール**が欠落。実測した瞬間と、それを引用する瞬間が構造的に分離していました。
- **教訓**: **「実測したことがある」≠「実測した」。** 時刻と状態は連続的に動く。
  再実測のコストは 1 件 1 秒程度で、常に実測し直す方が安い。
- **ゲート**: 部分的（`live-state-verify-guard` は無料 OSS 側に収録）。

### B-2. 文書を先頭 50 行だけ読んで「未登録」と結論した

- **症状**: 既に登録済みの設定について「これから新規作成してください」と案内し、
  重複作成を招いた。
- **構造**: 状態表が文書の**中盤〜末尾**にあった。「最初の N 行で十分」という
  読み方の習慣が、状態の結論に使われていました。
- **教訓**: **「文書を読んだ」≠「文書を読み切った」。** 一覧表・状態表は末尾に置かれる。
  全件読んで 1 秒未満なら、先読みで済ませる効率に意味はない。

### B-3. 一回きりの見積が要約を 5 層経て「日次の事実」に化け、公開物へ到達した

- **症状**: 公開予定の文章の核となる数字が、出典を辿ると**存在しない事実**だった。
- **構造**: 起点は一度きりのタスク見積（しかも当時訂正済みの誤り）。それが
  曖昧な要約文を経て「日次の恒常的な数字」と誤読され、
  素材台帳 → 戦略文書 → 生成コンテキストの「**検証済みの事実**」リスト → 本文、と
  **要約を経るたびに確信度だけが上がりました**。各層は前の層を信頼しただけで、
  誰も嘘をついていません。
- **同時に検出された同型汚染**: 「配信が 0 件（そもそも投稿されていない）」が
  「投稿したが反応 0」へ、意味が書き換わっていた。
- **教訓**: **生成エージェントが返す「事実」は、file:line まで遡れなければ採用しない。**
  既存の「サブエージェントの断定は再実測する」ルールを、状態報告だけでなく
  **コンテンツ生成にも適用する**。数値の事実性を検査する機械ゲートが無い限り、
  多層洗浄は必ず起きます。
- **ゲート**: ✅ 同梱 — `hallucination-rate-meter`（裏付けの無い主張の割合を採点）/
  `knowledge-citation-coverage`（主張に対する出典 URL の充足率）。

## C. 「実物を見ていない」系

### C-1. HTML に文字列が出ているのを見て「反映済み」と判定した

- **症状**: デプロイ直後から本番の表示が全面的に崩れた。検証は通っていました。
- **構造**: 検証が **HTML レイヤだけ**だった。HTTP 200 を確認し、HTML 内に目的の
  クラス文字列が出力されていることも確認済み。しかし**そのクラスの定義が
  CSS バンドルに生成されているか**は未確認で、スクリーンショットも撮っていなかった。
  文字列の出力と、スタイルの生成は**別レイヤ**です。
- **教訓**: UI 系の完了条件は 3 段必須 —
  ① HTTP 200 + 文字列 ② **バンドル内の定義** ③ **スクリーンショットによる目視**。
  追加コスト 5 分で防げます。

### C-2. HTTP 200 を見て「直った」と判定したが、本文が壊れていた

- **症状**: 500 エラーを修正し 200 が返るようになったので完了とした。
  実際に返っていた本文は、モデルの内部推論がそのまま漏れた壊れた出力だった。
- **教訓**: **API の検証はステータスで終わらせない（200 ≠ 正しい）。**
  ①ステータス ②本文の構造（期待キー・型）③**本文の中身を人間が 1 度読む** まで実施する。

### C-3. 「移行後に壊れている」を移行のせいにしかけた

- **構造**: 新環境で失敗を見ると移行起因と決めつけがちですが、
  **旧環境（未変更）に同じリクエストを 1 回投げる**だけで切り分けられます。
  実際、旧環境でも同じ失敗が出ており、既存不具合でした。
- **教訓**: 原因の帰属を誤ると、既存不具合を移行のせいにして無関係な箇所を触ります。

## D. 外部依存が、こちらが何もしないまま壊れる系

### D-1. ハードコードした外部 ID が、こちらが一行も触らないまま死んだ

- **症状**: 本番の一機能が全面的に失敗。コード変更履歴にも CI にも痕跡なし。テストは緑。
- **構造**: 外部プロバイダのモデル ID をハードコードしており、提供終了で消滅。
  さらに**フォールバックが同系統の 2 段**（同じ系列の新旧）だったため、
  系統ごと提供終了して**2 段とも同時に落ち、冗長化になっていませんでした**。
- **教訓**: 外部 ID をハードコードしたら「まだ生きているか」を定期実測する。
  **冗長構成は必ず別系統にする。** 検査は「一覧に載っているか」ではなく
  **実際に 1 回叩く**（一覧にあっても課金枠切れで呼べません）。

### D-2. 外部 API のフィールド名が先方の版更新で変わった

- **構造**: 廃止されたフィールドを送り続けて 400。またゴミ箱操作が冪等でなく、
  既に削除済みの対象への操作がエラーになりました。
- **教訓**: 外部 API のフィールド名は**こちらが一行も触らないまま**変わります。
  そして**エラー文言のマッチで分岐を書かない** — 同じ原因でも先方が文言や
  応答形式を変えた瞬間にすり抜けます。判定は「検査が成立したか」で書く。

### D-3. 壊れた設定ファイルが「有効」と表示された

- **構造**: YAML のブロックスカラーが本文の 1 行によって意図せず終端し、
  設定が壊れていました。しかしプラットフォーム側はこれをエラーにせず、
  一覧では `active` と表示。実際に起動して初めて 422 で判明しました。
- **教訓**: 一覧の `active` 表示は「動く」の根拠になりません。

## E. 並行実行が共有資源を壊す系

### E-1. 別セッションがステージしたファイルが自分のコミットに同乗した

- **構造**: 複数のエージェント/セッションが同じ作業ディレクトリを共有する運用では、
  git の index は**共有資源**です。「自分が add したもの = commit されるもの」という
  前提が成立しません。11MB のバイナリ 34 枚が同乗して公開されました。
- **教訓**: **コミットはパス束縛で行う**（`git commit -m ... -- <paths>`）。

### E-2. 「ガードが止めてくれるはず」を前提にしたテストが、本番に書き込んだ

- **構造**: 書き込み系ゲートの挙動テストを、fixture ではなく**実ファイル**に向けて実行。
  「今は feature ブランチだから main ガードが止める」と仮定していましたが、
  テスト実行の直前に**並行セッションが同じ作業ディレクトリを main に切り替えていた**ため
  ガードを通過し、テスト用のダミー行が本番に push されました（数分後に revert）。
- **教訓**: **止まることを検証するテストが、止まらなかったときに本番へ書く設計なら、
  それは fixture に向けるべきテスト**です。共有ディレクトリの「現在のブランチ」は
  安全前提に使えません。

### E-3. 素朴な union マージが 2 要素を 1 つに融合してデータを静かに消した

- **構造**: 複数の変更が同じ配列の末尾に要素を追記して衝突したとき、
  行単位の union マージは 2 つの要素を**1 つのオブジェクトに融合**させ、
  重複キーの後勝ちで要素が静かに消えました。マージは成功扱いです。
- **教訓**: 共有リスト/配列に行単位 union を使わない。要素単位で 3-way マージする
  決定論ドライバを書く。「union で解決した」は、**要素数と妥当性を実測するまで**信じない。

### E-4. タイトル検索で対象を特定し、無関係な対象を操作した

- **構造**: 対象を探すのにタイトル部分一致検索を使い、無関係なものを拾って
  自動マージを有効化してしまいました。当該コマンドは**成功しても無言**なので、
  確認するまで誤爆に気づきません（幸い競合状態で発火せず無傷）。
- **教訓**: 対象の特定は表示名の検索ではなく**識別子の照合**で行う。
  無言で成功するコマンドの後は、必ず状態を読み直す。

### E-5. 長時間実行中に、開始時刻を全レコードで使い回した

- **構造**: 76 行の同期に 51 秒かかる処理で、run 開始時のタイムスタンプを
  全行に適用。後半の行では実時刻との差が許容範囲を超え、
  **自分の書き込みが「人間の編集」として検出される**状態になりました。
- **教訓**: 長い run では時刻を 1 個で使い回さない。

## F. 人間ゲートが 2 経路あると、状態が読めなくなる

### F-1. 承認 UI が 2 系統あり、片方が他方を一切読まずに実行を完了させた

- **構造**: 承認経路が 2 つあり、一方（管理画面）が他方（チェックボックス）を
  **一切読まずに実行を完了**させます。そのためチェックボックスは永久に未チェックのまま、
  実態だけが進みます。「未チェック＝未実行」と読むと、**実行済みのものを
  『承認待ち』として提示し続ける**ことになります。
- **教訓**: **状態は実行側の記録（DB レコード・実行ログ）で判定する。**
  計画側のフラグを状態の根拠にしない。

## この台帳の使い方

新しい事故が起きたら:

1. **症状 / 構造 / 教訓** の 3 つで書く。「気をつける」で終わらせない
2. 教訓が**機械で検査できる形**なら、ゲートにする（`gate-forge` が scaffold を作ります）
3. できないなら、少なくとも**分母つきで観測**できる形にする

ゲートにできない教訓は、3 ヶ月で忘れられます。ここに並んでいるのは、
**忘れても壊れないところまで持っていけたもの**だけです。
