# 運用プラクティス — ゲートの外側で効くもの

ゲートにできることには限界があります。ここは**機械化できていないが、
実測で効果があった運用**をまとめたものです。同梱 skill が参照します。

---

## 1. セッション衛生

エージェントのセッションは、長くなるほど判断が鈍ります。原因は文脈の量そのものより、
**無関係な文脈の混入**です。

- **タスクが変わったらセッションを変える** — 探索 → 設計 → 実装 の段が変わる時、
  別コンポーネントの作業に移る時、独立したレビューを始める時
- **同一セッションで続けてよい** — 同一タスク内の実装 → テスト → コミット、
  エラー調査 → 修正、同じファイルの連続編集
- **要約（compact）は指示つきで** — 「現在の PR の文脈だけ残す」のように、
  何を残すかを明示する。無指示の要約は重要な制約から先に落ちます
- **誤った方向に進んだら、訂正プロンプトより巻き戻し** — 訂正で上書きしても、
  誤った文脈は残ります。残った誤りは後の判断に効きます

同梱の `context-bloat-tracker` と `session-length-compact-audit` が、
実際のセッション記録から肥大したセッションを検出します。

---

## 2. サブエージェントの使いどころ

サブエージェントは**文脈の隔離**が目的であって、並列化そのものが目的ではありません。

**使う**

- オープンエンドな探索（10 ファイル以上、または 3 つ以上の独立した探索軸）
- 依存関係がなく同時実行して安全なタスク群
- 大量のツール結果が主たる思考を汚染するリサーチ

**使わない**

- 単一ファイルの読み書き（直接読む方が速く正確）
- 1〜2 回の検索（起動コストが上回る）
- すでに十分な情報がある場面での再調査

**渡し方**: サブエージェントは呼び出し元の会話を見ていません。
背景・対象パス・制約・完了条件を**プロンプト内で自己完結**させます。
ここを省くと、サブエージェントは「それらしい」が的外れな結果を返します。

同梱の `subagent-usage-analyzer` と `retry-failure-classifier` が、
実際の起動履歴から過剰起動と失敗多発を検出します。

---

## 3. サブエージェントの断定を信じない

これは実測から出た、最も費用対効果の高いルールです。

**サブエージェントが返す「コミット済」「未実装」「壊れている」といった断定は、
呼び出し元が実測し直してから採用する。** ある監査では、サブエージェントの
critical 判定 4 件のうち **2 件が誤検出**でした。

さらに重要なのは、この規則を**状態報告だけでなくコンテンツ生成にも適用する**ことです。
生成物に載る数値は、要約を経るたびに意味が変質します
（[`incidents.md` B-3](incidents.md)）。数値は file:line まで遡れなければ採用しません。

## 4. ハーネスレビューの周期

ゲートは放っておくと腐ります。腐り方は 2 通りあり、**両方とも「緑のまま」進行します**。

- **Dead weight** — 対象が消えたのに残っているゲート。永遠に「0 件」を返す
- **偽の緑** — 依存が壊れて実行されなくなったゲート（[`incidents.md` A-1](incidents.md)）

**月次**でやること:

1. 全ゲートの `--self-test` を回し、**実行できた本数を分母つきで記録**する
2. 検出件数がゼロのゲートについて、「対象が無い」のか「走査していない」のかを確認する
3. 自然言語ルールのうち、機械検査に落とせるものを `gate-forge` で scaffold 化する
4. 3 ヶ月以上更新されていない skill を dead 候補として棚卸しする

同梱の `harness-kpi-ledger` が 1 と 3 の材料を、
`skill-lifecycle`（`harness-lint.py`）が 4 を出します。

## 5. ルールを増やす前に

自然言語のルールは、増えるほど 1 本あたりの効きが落ちます。常駐する文脈は有限だからです。

新しい事故が起きたとき、この順で検討します:

1. **機械で検査できるか** → できるならゲートにする（ルールは書かない）
2. **観測はできるか** → できるなら分母つきで計測する（判断は人間に残す）
3. **どちらも無理か** → 初めて自然言語のルールを 1 行足す

3 に落ちたルールは、**1 行**で書きます。経緯は別ファイルに置きます。
常駐文書が頻繁に書き換わると、モデルのプロンプトキャッシュが毎回無効化され、
コストと遅延の両方が悪化します。

同梱の `rule-promotion-extract` / `rule-promote-audit` / `rule-dedup-scan` が、
1 に昇格できるルールと重複ルールを機械的に抽出します。

## 6. コミットの規律

- **コミットはパス束縛で行う** — `git commit -m "..." -- <paths>`。
  複数のエージェント/セッションが同じ作業ディレクトリを共有する運用では、
  git の index は共有資源です（[`incidents.md` E-1](incidents.md)）
- **「なぜ」を書く** — prefix が正しくても「〜を更新」で終わるメッセージは、
  3 ヶ月後の自分にもエージェントにも何も伝えません

同梱の `commit-msg-quality-score` が、空虚なコミットメッセージを決定論的に採点します。

## 7. 報告の型 — 読む人はこの会話の経緯を覚えていない

報告を受け取る人は、セッションを多数並行しています。**この会話の経緯を前提にした報告は、単体では読めません。**
「結論から書く」だけでは足りず（結論が経緯に依存していれば同じ）、次の型で書きます。

1. **何を言われて、何をやったか** — 依頼の言い直しから始める
2. **結論** — できた / できない / 判断が要る
3. **詳細** — 実測値・成果物・リンク。**件数は必ず分母つき**（「走査 N 件のうち M 件」。「0 件」に分母が無いのは「測れていない」と区別がつかない）
4. **まとめ** — 次の一手。判断を仰ぐ項目は 1 件ごとに **①何を決めるか ②選択肢と結果 ③推奨と理由 ④判断しないと何が起きるか ⑤承認レベル**

上限を持ちます: **判断を仰ぐ項目は 1 報告に 3 件まで**（残りは件数だけ）。上限が無いと「3 件」を名乗りながら 10 件になります。
専門語・内輪語は普通の言葉に直し、要る略語は**初出で 1 行説明**します。長い作業は「今 step 3/5」と位置を言い直し、
本筋から外れる話は「別件:」で切り出します。3 系統以上が絡む複雑な報告は 1 枚の図解にします。

判断を仰いだ項目には**期限**を書きます。期限 + 14 日を過ぎた項目は「失効候補」として再提示せず、件数だけを出します
（④に書いた「判断しないと何が起きるか」が既に起きた = 結果で決まった扱い）。期限を書かない逃げ道を塞ぐため、期限が無ければ起票 + 30 日を暫定期限とします。

引き継ぎ文書（HANDOFF・action list）も同じ理由で**上限**を持ちます。完了した節は archive へ移し、本体には行数の上限（floor）を書き、
上限は**下げる方向にしか動かせません**。読む側が人でも「文脈で届かないものは存在しない」のは同じです。

型は自然言語で書いても自己申告なので守られません。同梱の `scripts/report-shape-check.py`（4 段・5 点・上限・分母・内輪語）と
`scripts/state-doc-shape-check.py`（floor・完了節の残留・取り消し線の残留）が形を数えます。

参照（一次情報）: Böckeler「harness = guides + sensors」（martinfowler.com・2026-04）／ OpenAI「文脈で届かないものは存在しない」（Harness engineering・2026-02）／
statusline 実践「4 項目から始め、1 項目足すごとにその権利を得る」（2026-07）。
